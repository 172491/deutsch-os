# 项目档案｜通讯板

> 状态：方向已确认，具体技术细节可在正式重写时继续校准。

## 1. 核心需求

通讯板解决的不是“让 Eleanor 随时知道所有人的状态”，而是：

- 在猫头鹰不适合、距离较远或需要快速联系时传递有限信息；
- 让不同学院 / 家庭之间拥有不完全依赖公共渠道的联系手段；
- 在危机中提供求援可能，但不保证一定被看见、一定来得及响应。

## 2. 项目分工

- **Alexis**：提出总体需求、主要架构、信息传输与接口思路，负责大量实验整合。
- **Fred / George**：原型反馈、操作逻辑、伪装 / 实用化、极端使用测试；必须拥有自己的设计贡献。
- **Draco**：早期远程真实用户，提供使用反馈和纯血家庭场景意见；不是因为亲密而成为项目共同所有者。
- **Shafiq 技术网络**：稳定化、专业魔咒补足、制造一致性与后续规模化评估。

## 3. 必须保留的限制

至少保留以下几类中的多项：

- 传输延迟；
- 信号 / 魔力噪声；
- 耗魔或持续使用限制；
- 距离 / 环境影响；
- 接收者必须主动查看，不能保证求救一定被及时发现；
- 存储容量有限；
- 设备损坏、遗失或被隔绝时失效；
- 隐私和身份识别不能天然完美。

通讯板的存在不能让“信息差”从小说中消失。

## 4. 关系作用

### Fred / George

这项合作必须把他们从“帮 Alexis 做东西的人”改成平等创造者。后续即使合作中断，也应来自课表、魁地奇、他们自己的项目和商业野心，而不是等主角召唤。

### Draco

早期测试说明 Alexis 愿意把未完成的东西交给他真实使用，也愿意听取挑刺意见；但这种信任不能演变成默认监控权限。

### Shafiq

通讯板是“学生原型”第一次真正进入工程化 / 产业化网络的重要节点。关系因此从私人支持推进为可谈判的专业合作。

## 5. 第二部高潮约束

通讯板只能做到“发出信息的可能性更高”。真正完成救援仍依赖：

- 有人看到；
- 有人相信；
- 有人知道如何行动；
- Draco / Snape 等独立作出判断。

技术成功不能替代人物选择。
